# MCPeas Architecture Standard

## One default architecture

The default is a hosted TypeScript MCP Apps server generated by `create-mcp-use-app` with the `mcp-apps` template.

Use this even for tool-only v1 projects because it keeps the repo widget-ready, gives Codex a consistent layout, and avoids rewriting the server when the user later asks for a UI.

```bash
npx create-mcp-use-app <project-name> --template mcp-apps
cd <project-name>
npm run dev
```

If the surrounding repo already uses pnpm, use the CLI's package-manager flag instead of introducing npm lockfile churn.

## Project shape to converge on

```text
<project>/
  AGENTS.md
  .codex/
    config.toml
    agents/
      code-mapper.toml
      docs-researcher.toml
      mcp-reviewer.toml
  docs/
    mcpeas/
      spec.md
      runbook.md
      research.md
  evals/
    golden-prompts.json
  index.ts
  resources/
    <widget-name>/
      widget.tsx
      components/
  public/
  package.json
  tsconfig.json
```

The exact mcp-use scaffold may evolve; preserve its generated layout and add the MCPeas files around it.

## Implementation order

1. Write `docs/mcpeas/spec.md` first.
2. Scaffold or detect the project.
3. Add Codex harness files.
4. Implement mock-backed tool handlers.
5. Add widgets only where interaction or visual inspection materially improves the job.
6. Replace mock data with real API/storage.
7. Add auth only when needed.
8. Run tests and Inspector.
9. Update docs/runbook from what actually works.

## Tool inventory standard

Each tool must be specified before implementation:

```md
### <tool-name>

Use this when...
Do not use when...

Input:
- `field`: type, validation, examples

Output:
- `structuredContent`: concise model-visible JSON
- `content`: short narration, if useful
- `_meta`: widget-only detail, large data, or sensitive-but-user-visible detail

Annotations:
- readOnlyHint:
- destructiveHint:
- openWorldHint:

Auth:
- anonymous / OAuth / service token / admin-only
```

## Payload boundary standard

`structuredContent` is for the model and should be small, stable, and non-secret.

`content` is optional model-visible narration. Use it sparingly; the model can narrate from `structuredContent`.

`_meta` is for the widget and host. It is not shown to the model, but still treat it as user-visible and never store secrets there.

## Widget standard

Use a widget when the user must inspect, compare, select, edit, preview, or iterate. Do not build a widget for scalar answers like "status is healthy" unless it belongs to a larger dashboard.

Widget resources must be MCP Apps-compatible:
- MIME type: `text/html;profile=mcp-app`
- stable URI for compatible changes
- versioned URI for breaking changes
- explicit CSP for external domains
- explicit widget domain before submission
- bridge-first design; feature-detect ChatGPT-only `window.openai`

## Auth standard

Default to anonymous/read-only for demos and public data. Require OAuth when:
- user-specific data is read
- writes/mutations happen
- private resources are accessed
- quotas, billing, or account linking matter

Do not trust locale, user-agent, location, or other client hints for authorization.

## Hard-stop deviations

Use another architecture only when the user explicitly needs it or the environment forces it:
- Rust `rmcp`: use for explicit Rust production requirement or deeply Rust-native host.
- Python/FastMCP: use for existing Python data/science backends where a TypeScript edge service is wasteful.
- stdio/MCPB/local: use for filesystem, desktop, localhost, device, or OS-bound tasks.
- generic MCP SDK: use when mcp-use cannot express a required protocol feature.

When deviating, still keep the MCPeas spec, golden prompts, and Codex harness.
